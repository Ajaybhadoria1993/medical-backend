Treatment plan database schema

Every table, every column and every relationship in the module. Read the diagram for the shape, the relationship register for the rules, and the table cards for each column's purpose.

Design rules behind this model

  1. One table per real thing: template, plan, step, step-to-visit link, money entry.
  2. Store facts, calculate states. "Booked" and "Arrived" come from the linked appointment; balance comes from ledger rows; "late" comes from dates.
  3. Money and history are append-only. They have no updated_at; corrections are new rows.
  4. A plan copies its template. Editing a template never changes an existing patient's plan.
  5. Configurable, not hard-coded. Steps, gaps, sessions, fees and specialty fields are rows, never code.
  6. Module boundary. Links to existing tables are stored IDs with no foreign key, so the module can be separated later.

How data moves: one patient, start to finish

Example: Rahul Sharma, root canal on tooth 36, ₹11,000, 5 steps. Each stage lists the rows written. Gold table names are existing tables owned by other modules; the plan module never writes them directly.

Outside the module

  1. No existing table changes. 'Treatment' is a new value of the free-text appointments.appointment_type.
  2. Outside work (lab, scan) tracking is not in Phase 1; it comes with Dental in Phase 2.
  3. No branches in Phase 1; a nullable branch_id is added to templates and plans with the branch feature.
  4. Migrations are generated by the repo owner from these models.
